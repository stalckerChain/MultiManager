# TASK — Информационная вкладка профиля при запуске

## Цель

При нажатии «Старт» открывать в браузере профиля новую вкладку с информацией
об аккаунте. Страница должна загружаться через публичный локальный HTML
endpoint и иметь заголовок вкладки, равный имени аккаунта.

Режимы запуска:

- ручной запуск профиля из MultiManager;
- запуск профиля через `stAuto0` в режиме MultiManager.

Legacy-режим `stAuto0` и его текущую логику запуска не изменять.

## Содержимое страницы

Страница `/profile-info/:profileId` должна показывать только следующие поля:

- `name`;
- `email`;
- `wallet_evm_address`;
- `wallet_sol_address`;
- `twitter_username` как X username;
- `discord_username`;
- IP прокси (`last_ip`);
- локация прокси (`location`).

Значения отсутствующих полей отображать единообразным безопасным placeholder,
например `Не указано`.

Не включать в HTML, JSON или клиентский код:

- `email_password`;
- `wallet_password`;
- `twitter_password`;
- `twitter_auth_token`;
- `twitter_email`;
- `discord_password`;
- `discord_token`;
- `discord_email`;
- proxy username/password;
- fingerprint seed и другие поля, не входящие в согласованный список.

## Согласованное решение

1. Добавить публичный локальный HTML endpoint:

   ```text
   GET /profile-info/:profileId
   ```

2. Endpoint получает профиль и связанный прокси из существующих query-объектов,
   формирует безопасную проекцию данных и возвращает HTML.
3. Endpoint возвращает `404`, если профиль не найден.
4. Все пользовательские значения экранировать перед вставкой в HTML. Имя
   аккаунта использовать и в `<title>`, и в заголовке страницы.
5. Не переиспользовать `GET /api/profiles/:id`, поскольку тот endpoint
   возвращает секретные поля профиля.
6. Endpoint разместить в отдельном API-модуле публичной зоны и подключить до
   общего `authMiddleware`. Он предназначен только для локального браузера
   MultiManager; публичная авторизация для него не добавляется по согласованию.
7. В обработчике `POST /api/browser/:id/start` после готовности CDP, загрузки
   расширений и существующих launch/preflight-операций создать новую page
   target с URL:

   ```text
   http://127.0.0.1:<MultiManager-port>/profile-info/<profileId>
   ```

   Использовать существующий CDP-клиент и не создавать новый механизм
   подключения. URL не включать в логи.
8. Порт брать из `req.socket.localPort` исходного `POST /api/browser/:id/start`.
   Это фактический порт HTTP-сервера, принявшего запрос GUI или `stAuto0`;
   передавать порт через `spawnBrowserWithCdp`, менять `src/index.js` и
   хардкодить `3000` не нужно. `req.socket.localPort` GET-запроса страницы для
   этой цели не использовать: он выполняется уже после создания target.
9. Создание информационной вкладки не должно останавливать профиль. Перед
   обращением к CDP явно проверить наличие `cdpPort`; если порт отсутствует,
   записать warning и продолжить успешный запуск. Ошибка
   `Target.createTarget` также записывается безопасно и не ломает ответ
   успешного запуска, если браузер уже готов.
10. Безопасный лог ошибки должен содержать только `profileId` и очищенное
    сообщение/категорию ошибки без stack trace, URL, содержимого страницы,
    имени аккаунта и других данных профиля. Не логировать исходный CDP-текст,
    если в нём могут присутствовать URL или параметры страницы.
11. Создание информационной вкладки выполняется в самом конце обработчика
    `POST /:id/start`: после `loadExtensionsViaCDP`, после блока
    `if (!runId) { await runManualAutologin(...) }` и непосредственно перед
    `res.json(...)`. Это не позволяет ручному preflight удалить новую вкладку
    и использует одну точку для ручного и automation/MM запуска.
12. Существующее поведение очистки вкладок и автологина не расширять за рамки
    этой задачи. Новая информационная вкладка создаётся после соответствующих
    стартовых операций.

## Затрагиваемые файлы

### Backend

- `src/api/profile-info.js` — новый публичный HTML endpoint, безопасная
  проекция данных, HTML escaping и `module.exports = router` без фабрики.
- `src/core/app.js` — подключение публичного endpoint до `authMiddleware`.
- `src/api/browser.js` — создание информационной вкладки через CDP в конце
  запуска профиля; проверка `cdpPort`; обработка ошибки без падения запуска;
  получение порта из `req.socket.localPort` start-запроса.
- `src/cdp/client.js` — изменять только если существующих CDP-примитивов
  недостаточно; предпочтительно оставить файл без изменений.

### Тесты

- `tests/unit/profile-info.test.js` — новый endpoint: 200, 404, безопасные
  поля, отсутствие секретов, escaping HTML и корректный `<title>`.
- существующий тест browser launch или новый минимальный тест в
  `tests/unit/browser-start-await.test.js`/отдельном browser-тесте — проверка
  вызова `Target.createTarget` с URL информационной страницы для ручного и
  automation/MM запуска.
- при наличии подходящего интеграционного шва расширить
  `tests/integration/profile-launch.test.js`; реальный CloakBrowser тест не
  делать обязательным для обычного `npm test`.

### Документация

- `docs/API.md` — отдельный раздел в формате существующих `### GET ...`:
  публичный локальный endpoint без авторизации, список полей и ограничение
  использования только на loopback.
- `docs/API.en.md` и `docs/API.zh.md` — синхронно обновить соответствующий
  раздел, если документация поддерживает этот endpoint во всех переводах.

Не изменять `package.json`, lock-файлы, схему БД и версию проекта.

## Проверка результата

1. Запустить unit-тесты endpoint и browser launch:

   ```bash
   npm test -- --run tests/unit/profile-info.test.js
   ```

   и соответствующий тест запуска браузера.

2. Запустить полный набор:

   ```bash
   npm test
   ```

3. Ручная проверка на Windows:

   - запустить профиль из GUI;
   - убедиться, что появилась новая вкладка;
   - проверить title вкладки равен `name` аккаунта;
   - проверить все согласованные поля и placeholder для пустых значений;
   - убедиться, что пароль и токены не отображаются.

4. MM-проверка:

   - запустить профиль через `stAuto0` в режиме MultiManager;
   - убедиться, что URL содержит правильный UUID профиля;
   - проверить, что отображаются данные именно этого профиля;
   - проверить работу при нестандартном порте MultiManager.

5. Проверить ошибки:

   - неизвестный `profileId` возвращает 404;
   - отсутствие proxy не приводит к ошибке страницы;
   - отсутствие IP/location отображается placeholder;
   - сбой CDP создания вкладки не переводит уже запущенный профиль в failed.

6. Отдельно проверить legacy-запуск `stAuto0`: его текущий launch-flow не
   изменён.

## Риски и ограничения

- Endpoint будет без авторизации по согласованию пользователя. Даже при
  binding на `127.0.0.1` любой локальный процесс, знающий UUID профиля, сможет
  прочитать отображаемые данные аккаунта.
- UUID профиля не считать механизмом авторизации.
- Отдельный rate limiter для `/profile-info/:profileId` не добавлять: endpoint
  loopback-only, а запуск большого числа профилей параллельно не должен
  блокироваться ограничением вроде 60 запросов в минуту. Это осознанное
  ограничение публичного локального endpoint.
- IP/location могут быть устаревшими, если прокси не проверялся или GeoIP
  сервис недоступен. Страница должна показывать фактически сохранённые данные,
  не выполнять отдельный внешний GeoIP-запрос из браузера.
- HTML должен формироваться только из безопасной проекции и с escaping, чтобы
  имя или username не могли внедрить markup/script.
- При ручном запуске существующий автологин и очистка вкладок выполняются до
  создания информационной вкладки.
- При MM-запуске `stAuto0` может после старта открыть дополнительные вкладки;
  эта задача отвечает за создание информационной вкладки, но не меняет
  существующую MM-логику логина и очистки вкладок.

## Критерии приёмки

- После старта профиля появляется новая вкладка с информацией именно этого
  профиля.
- Заголовок вкладки равен имени аккаунта.
- Страница работает одинаково при ручном и MM-запуске.
- Отображаются все восемь согласованных групп данных: имя, email, EVM,
  SOL, X, Discord, IP и location прокси.
- Секретные поля отсутствуют в HTML-ответе и логах.
- Ошибка страницы не ломает уже успешный запуск браузера.
- Legacy-flow, API схемы БД, зависимости и версия проекта не изменены.
- Unit-тесты и полный `npm test` проходят.
