# TASK — Распределение прокси по аккаунтам

## Цель

На вкладке «Прокси» добавить две операции:

- «Распределить используемые прокси» — взять уникальные прокси, назначенные
  хотя бы одному аккаунту, проверить их и перераспределить рабочие прокси по
  всем аккаунтам.
- «Распределить все прокси» — взять все прокси из базы данных, проверить их и
  перераспределить рабочие прокси по всем аккаунтам.

Распределение выполняется случайно. В рамках одного цикла уже назначенные
прокси временно исключаются из выборки. Когда рабочие прокси заканчиваются,
начинается новый цикл с полным списком рабочих прокси.

## Согласованные требования

- В целевую группу входят все записи `profiles`, включая аккаунты без текущего
  прокси и аккаунты со статусом `running`.
- Переназначение допускается для запущенных аккаунтов. Оно меняет `proxy_id` в
  базе данных и не перезапускает уже открытый браузер.
- Для режима «используемые» источник — уникальные `proxy_id` профилей с
  ненулевым `proxy_id`.
- Для режима «все» источник — все записи таблицы `proxies`, независимо от
  предыдущего значения `is_active`.
- Каждый прокси из источника проверяется последовательно через существующую
  проверку прокси. Ротация мобильного прокси должна выполняться тем же способом,
  что и в `POST /api/proxies/:id/check`, до проверки соединения.
- В распределение попадают только прокси, для которых проверка вернула
  `ok: true`. Значение `is_active` до текущей проверки не является заменой
  актуальной проверке.
- До изменения аккаунтов пользователь должен увидеть подтверждающее popup-окно
  в стиле существующего подтверждения удаления. В popup отображаются минимум:
  количество проверенных прокси, рабочих прокси, нерабочих прокси и аккаунтов,
  которые будут перераспределены.
- Отмена popup не изменяет назначения.
- После подтверждения назначения обновляются одной SQLite-транзакцией.
- Если рабочих прокси нет, текущие назначения сохраняются, операция не выполняет
  массовое обнуление `proxy_id`, а GUI показывает сообщение о проблеме.
- Если проверка отдельных прокси завершается ошибкой, обработка продолжается;
  такие прокси считаются нерабочими и не используются.
- Не менять схему БД, версии проекта и существующее поведение CRUD/check API.
- Не передавать и не возвращать в новых ответах username/password прокси.
- Все новые пользовательские строки добавить через i18n во все поддерживаемые
  локали.

## Архитектурное решение

Использовать двухфазную операцию, чтобы сначала проверить прокси и показать
результаты, а назначать их только после явного подтверждения пользователя.

### Фаза 1: предварительная проверка

Добавить защищённый endpoint, например:

```text
POST /api/proxies/distribute/preview
{ "mode": "used" | "all" }
```

Endpoint должен:

1. Валидировать `mode`.
2. Получить исходный список прокси согласно режиму.
3. Последовательно проверить каждый прокси существующим `checkProxy` и
   существующей логикой rotation-прокси.
4. Обновить текущие технические поля проверки (`is_active`, `last_ip`, время
   проверки и доступную геолокацию) так же, как существующий endpoint проверки.
5. Получить все профили и вернуть безопасный preview без proxy credentials:

```json
{
  "mode": "used",
  "profiles_count": 10,
  "checked_count": 5,
  "working_count": 4,
  "failed_count": 1,
  "working_proxy_ids": [1, 2, 3, 4]
}
```

Список `working_proxy_ids` нужен второй фазе. Backend должен на второй фазе
проверять, что переданные ID принадлежат допустимому источнику выбранного
режима, чтобы preview нельзя было подменить прокси из другой выборки.

### Фаза 2: подтверждённое распределение

Добавить endpoint, например:

```text
POST /api/proxies/distribute
{
  "mode": "used" | "all",
  "working_proxy_ids": [1, 2, 3, 4]
}
```

Endpoint должен:

1. Повторно получить профили и допустимый источник для `mode`.
2. Проверить, что `working_proxy_ids` являются прокси из этого источника.
3. Не выполнять повторную сетевую проверку после подтверждения, поскольку
   preview уже был показан пользователю. Если список пуст, вернуть понятную
   ошибку и не менять профили.
4. Сформировать назначения в стабильном порядке аккаунтов, например по
   `profiles.number`.
5. Для каждого аккаунта выбрать случайный прокси из оставшихся в текущем цикле;
   после исчерпания списка восстановить полный список рабочих прокси.
6. Обновить только `profiles.proxy_id` внутри одной транзакции.
7. Вернуть количество назначенных аккаунтов и использованных прокси.

Выбор случайного прокси должен использовать `Math.random` или существующий
проектный подход без добавления зависимости. В тестах случайность должна быть
контролируемой через mock, либо проверяться инварианты алгоритма: назначение
только рабочих прокси, отсутствие повторов внутри цикла и повторное начало
цикла после исчерпания списка.

Не создавать отдельную таблицу или постоянную сущность для preview. Состояние
preview передаётся между фазами только безопасными числовыми ID, а финальный
endpoint повторно валидирует принадлежность ID источнику.

## План реализации

### 1. Backend и запросы БД

В `src/db/queries.js`:

- добавить запрос получения уникальных прокси, используемых профилями;
- добавить batch-обновление `proxy_id` для списка профилей в транзакции или
  минимальный query-метод, который вызывается из транзакции роутера;
- не менять существующий контракт `createProfileQueries.update` для одиночного
  редактирования профиля.

В `src/api/proxies.js`:

- добавить endpoint preview и endpoint подтверждённого распределения сразу
  после `const router = express.Router();`, до первого маршрута
  `router.get('/:id')` (то есть до всех существующих параметризованных
  `/:id` маршрутов);
- переиспользовать существующую логику `rotateProxy`, `checkProxy`, обновления
  `is_active`, `last_ip` и location;
- вынести общий код проверки во внутреннюю неэкспортируемую функцию модуля,
  чтобы его использовали одиночный `POST /:id/check` и preview batch-операции,
  не расширяя публичный API модуля и не дублируя поведение проверки;
- продолжать проверку после ошибки отдельного прокси;
- не логировать credentials, полный connection string или результаты с секретами;
- для пустого списка профилей корректно вернуть preview и не выполнять записи.

Проверить существующие callers API и не изменять CRUD, timezone endpoint и
проверку одиночного прокси по смыслу.

## Риски и контроль

- **Длительная последовательная проверка:** при большом числе прокси операция
  может занять до нескольких таймаутов на каждый прокси. GUI обязан показывать
  loading, а backend не должен ограничиваться слишком коротким HTTP timeout.
  Не добавлять параллельность без отдельного согласования.
- **Проверка rotation-прокси:** rotation может менять внешний IP и занимает
  время; использовать существующий порядок rotation → ожидание → check.
- **Работающие профили:** изменение `proxy_id` не меняет уже запущенный браузер.
  Это ожидаемое согласованное поведение; новые назначения применяются при
  следующем запуске.
- **Нулевой результат:** при отсутствии рабочих прокси запрещено очищать или
  частично изменять текущие назначения.
- **Устаревший preview:** между фазами список прокси может быть изменён. Финальная
  фаза должна повторно валидировать ID и атомарно отказаться от записи при
  несоответствии.
- **Конкурирующие операции:** пока одна операция выполняет preview или
  подтверждение, GUI блокирует повторный запуск. Backend-транзакция защищает
  только запись, поэтому разработчик должен проверить поведение при двух
  параллельных API-вызовах.
- **Секреты:** preview и ответы распределения возвращают только числовые ID и
  счётчики; credentials прокси не должны попадать в JSON, логи или сообщения.
- **Частичная проверка:** нерабочий прокси не останавливает batch, но причина
  ошибки не должна раскрывать username/password.

## Проверка

Из корня проекта:

```text
npm test
npm run lint
```

Сборка GUI:

```text
cd gui && npm run build
```

Ручная проверка:

1. Создать несколько прокси и аккаунтов, включая аккаунт без прокси и
   запущенный аккаунт.
2. Назначить прокси только части аккаунтов и проверить режим «используемые».
3. Проверить, что все кандидаты проверяются последовательно и preview показывает
   правильные количества рабочих/нерабочих прокси.
4. Отменить popup и убедиться, что `proxy_id` аккаунтов не изменился.
5. Подтвердить операцию и проверить перераспределение всех аккаунтов.
6. Проверить повторное использование прокси, когда аккаунтов больше, чем
   рабочих прокси, и отсутствие повторов внутри одного цикла.
7. Проверить режим «все прокси», включая ранее неиспользуемые прокси.
8. Проверить сценарий, в котором все прокси нерабочие: назначения сохраняются,
   пользователь получает сообщение о проблеме.
9. Проверить работающий аккаунт: его текущий браузер не перезапускается, а новое
   назначение сохраняется для следующего запуска.
10. Проверить ошибки сети/timeout и отсутствие credentials в логах и ответах.

## Критерии готовности

- На вкладке прокси доступны обе согласованные кнопки.
- Preview последовательно проверяет правильный набор прокси.
- Пользователь видит popup с результатами до изменения аккаунтов.
- Отмена popup не меняет назначения.
- После подтверждения все аккаунты получают случайные назначения только из
  рабочего набора с циклическим повторным использованием.
- Запущенные аккаунты также обновляются в БД без перезапуска браузера.
- При отсутствии рабочих прокси текущие назначения сохраняются.
- Нет утечки proxy credentials в API, UI или логах.
- Существующие CRUD/check/delete операции прокси не регрессировали.
- Unit-тесты, lint и GUI build проходят.
- БД, версия проекта и unrelated-файлы не изменены.
