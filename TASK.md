# TASK — Уведомление о нерабочем прокси при запуске профиля

## Цель

При нажатии `Start` пользователь должен получать видимое уведомление, если профиль не запустился из-за недоступного прокси. В уведомлении обязательно указывать имя профиля.

Пример сообщения:

```text
Профиль «Имя профиля» не запущен: прокси недоступен.
```

## Подтверждённое текущее поведение

Backend уже проверяет прокси до запуска CloakBrowser:

```text
src/api/browser.js:407-445
```

При неудачной проверке он:

1. Переводит профиль в `stopped`.
2. Записывает в лог профиля `Прокси недоступен` и техническую причину.
3. Возвращает ошибку `412 PRECONDITION_FAILED` с текстом `Прокси недоступен`.

Axios-клиент переносит серверные `error` и `code` в обычный объект `Error`:

```text
gui/src/renderer/api/client.js:29-39
```

GUI сейчас только пишет ошибку в консоль и не показывает её пользователю:

```text
gui/src/renderer/views/Profiles.vue:264-271
```

В этой же странице уже используется `message` из Ant Design Vue для уведомлений о проверке прокси, поэтому новый механизм уведомлений создавать не нужно.

## Согласованное решение

Обработать ошибку в существующей функции `startProfile(id)` в `gui/src/renderer/views/Profiles.vue`.

Алгоритм:

1. До запроса запуска найти профиль в `profilesStore.profiles` по `id` и сохранить его имя.
2. В `catch` проверить `err.code === 'PRECONDITION_FAILED'`.
3. Для этой ошибки показать `message.error` или эквивалентное существующее уведомление с именем профиля и причиной недоступного прокси.
4. Для остальных ошибок запуска также показывать уведомление с именем профиля, но не маскировать исходный текст ошибки.
5. Сохранить текущий `console.error` для диагностики.
6. Сохранить текущий `finally` с обновлением списка профилей.

Текст для ошибки прокси должен явно сообщать, что профиль не запущен, а не только что прокси недоступен.

Пример допустимой реализации поведения:

```text
Профиль «{profileName}» не запущен: прокси недоступен.
```

Если имя не найдено, использовать безопасный fallback вроде идентификатора профиля, чтобы уведомление всё равно было показано.

## Затрагиваемые файлы

### Обязательно

```text
gui/src/renderer/views/Profiles.vue
```

Изменить только обработку ошибки в `startProfile()` и, при необходимости, импорт/вызов уже используемого `message`.

### Тесты

Проверить существующую структуру тестов GUI. Если для `Profiles.vue` уже есть подходящий unit-тест, добавить проверки туда. Если тестовой обвязки для Vue-компонентов нет, не создавать крупную новую инфраструктуру: выполнить доступную сборку GUI и ручную проверку.

Новый backend-тест не требуется: контракт `412 PRECONDITION_FAILED` уже существует, а изменение касается отображения ошибки в GUI.

## Ограничения

- Не менять проверку прокси в `src/api/browser.js`.
- Не менять HTTP-код, статус или контракт API.
- Не менять поведение запуска профиля без прокси.
- Не менять массовый запуск: `bulkStart()` уже вызывает `startProfile()`, поэтому уведомление должно работать и для него автоматически.
- Не показывать технические credentials прокси.
- Не логировать пароль или другие секреты.
- Не изменять БД, миграции, версию проекта и `TASK.md` после начала реализации.
- Не создавать новый сервис, store или глобальный менеджер уведомлений.

## Проверка

### Автоматическая

Из корня MultiManager выполнить:

```text
npm test
```

Из каталога GUI выполнить доступную проверку сборки:

```text
cd gui && npm run build
```

Если полноценная сборка требует внешних условий, выполнить доступные unit-тесты GUI и зафиксировать причину невозможности полной сборки.

### Ручная

1. Запустить MultiManager.
2. Создать или выбрать профиль с заведомо нерабочим прокси.
3. Нажать `Start` на главной странице профилей.
4. Убедиться, что отображается уведомление с именем профиля и текстом о том, что профиль не запущен из-за недоступного прокси.
5. Убедиться, что профиль остаётся в статусе `stopped`.
6. Выбрать профиль без прокси или с рабочим прокси и убедиться, что успешный запуск не показывает ошибку.
7. Проверить массовый запуск нескольких профилей, включая профиль с нерабочим прокси: уведомление должно содержать имя именно проблемного профиля.
8. Проверить, что в логах приложения не появились пароли или credentials прокси.

## Критерии готовности

- При нерабочем прокси пользователь видит уведомление, а не только запись в DevTools Console.
- В уведомлении есть имя профиля.
- В уведомлении явно указано, что профиль не запущен из-за прокси.
- Профиль после ошибки имеет статус `stopped`.
- Рабочий запуск не регрессировал.
- Массовый запуск использует то же уведомление.
- Backend API и проверка прокси не изменены.
- Тесты и сборка, доступные в окружении, проходят.
