# TASK — Синхронизатор вкладок и multi-control

## Цель

Переименовать вкладку `Window Arranger` в `Синхронизатор`, перенести управление
Sync из `Profiles` в эту вкладку и добавить массовые операции с вкладками всех
запущенных профилей.

Операции выполняются для профилей со статусом `running`. Ошибка одного профиля
не должна останавливать обработку остальных; GUI показывает итоговую сводку и
ошибки по отдельным профилям/ссылкам.

## Согласованные требования

- Область GUI `/arranger` сохраняется, меняются её навигационное имя и заголовок.
- Кнопка/меню Sync удаляются из `Profiles.vue` и переносятся в синхронизатор.
- Sync должен продолжать работать при выполнении операций с вкладками.
- «Закрыть все вкладки» для каждого running-профиля сначала создаёт новую
  вкладку `about:blank`, затем закрывает все остальные page-вкладки.
- Форма ссылок принимает несколько строк. Пустые строки пропускаются.
- Для каждой непустой строки и каждого running-профиля создаётся отдельная
  вкладка с этой ссылкой.
- Разрешены любые ссылки по явному решению пользователя. Не добавлять
  ограничение только на `http/https` и не добавлять SSRF-фильтр в рамках этой
  задачи.
- URL, ссылки, токены и другие секретные значения не логировать.
- Операции должны продолжаться после ошибок и возвращать структурированный
  результат с количеством успешных/неуспешных действий и деталями ошибок.
- Не менять схему БД и версию проекта.

## Архитектурное решение

Добавить общий CDP-слой для адресных операций с вкладками, не используя
внутренние `browserConnections` `CdpManager` как единственный источник.
Источником CDP-порта должен быть существующий экспортированный метод
`getCdpPort(profileId)` из `src/api/browser.js` (строка 148), а не повторный
поиск порта через БД, PID или GUI:

1. Для каждой команды определить список running-профилей через существующие
   profile queries.
2. Получить CDP-порт конкретного профиля через
   `require('../api/browser').getCdpPort(profileId)`.
3. Создать краткоживущую CDP-сессию, явно связанную с `profileId`.
4. Получать page targets конкретного профиля и передавать `targetId` во все
   операции `Target.createTarget`/`Target.closeTarget`.
5. Закрывать CDP-сессию в `finally`, чтобы операции разных профилей не
   смешивали WebSocket, target или session ID.

Существующий `CdpManager` продолжает обслуживать multi-control. Новый слой
должен использовать общий низкоуровневый CDP-клиент, но не изменять mapping
master/slave и не отправлять команды через master автоматически.

При активном Sync необходимо учитывать гонки: создание вкладки может быть
обнаружено multi-control как новый tab мастера. Новый endpoint должен выполнять
операцию с явным `profileId`; разработчик обязан проверить, что созданные
вкладки не ошибочно закрываются как чужие и что mapping Sync не получает
непредсказуемые target ID. При необходимости операция должна временно
зафиксировать набор target ID до создания новых вкладок и закрывать только
вкладки из этого набора.

## План реализации

### 1. Общий CDP-слой

Создать `src/cdp/profile-tabs.js`, использующий
`require('../cdp/client')` для существующих примитивов `call`, `connect` и
`discoverWsUrl`, а также `require('../api/browser').getCdpPort` как источник
порта. `src/cdp/client.js` не менять: его существующих низкоуровневых
примитивов достаточно.

`createCdpSession(port)` в `src/api/browser.js` (строка 775) не расширять и не
использовать как основу нового слоя. Он предназначен для одной операции над
одним target: сам выбирает или создаёт первый page-target, attach-ит его и
возвращает ограниченный интерфейс `send/close`. Для этой задачи требуется
явная адресация `profileId → port → targetId`, получение полного списка targets,
создание нескольких вкладок и закрытие конкретных targets. Расширение
`createCdpSession` скрыло бы нужные target ID и создало бы лишнюю связь
массовых операций с browser API. Новый `profile-tabs.js` должен напрямую
использовать низкоуровневый CDP-клиент и гарантировать закрытие собственного
WebSocket.

В выбранном варианте реализовать минимальные переиспользуемые операции для
временного подключения к CDP-порту профиля:

- подключение и гарантированное закрытие WebSocket;
- получение только page targets;
- создание target с переданным URL;
- закрытие target по его ID;
- обработка timeout, CDP error и недоступного профиля.

Не дублировать CDP WebSocket-код в роутере и не изменять поведение
`createCdpSession` для существующих browser API callers.

### 2. Backend API

В `src/api/window-arranger.js` добавить:

- `POST /api/window-arranger/close-all-tabs`;
- `POST /api/window-arranger/open-links` с JSON-телом `{ links: string[] }`.

Поведение `close-all-tabs`:

- выбрать running-профили;
- для каждого получить исходный список page targets;
- создать новую `about:blank`;
- закрыть исходные targets, не закрывая созданную вкладку;
- вернуть результат по каждому профилю.

Поведение `open-links`:

- проверить, что `links` является массивом строк;
- удалить пустые строки, сохранив порядок;
- для каждого running-профиля последовательно или с ограниченным параллелизмом
  создать по одной вкладке на каждую ссылку;
- не включать URL в логи и сообщения ошибок, если это не требуется для
  диагностики;
- продолжать обработку после ошибки отдельной ссылки или профиля.

Ограничить параллелизм на уровне профилей/вкладок так, чтобы операция для
100+ профилей не создавала неуправляемый взрыв CDP-соединений. Не добавлять
новую БД-сущность или отдельный runtime-manager.

## Риски и контроль

- **Активный Sync:** target discovery может воспринять созданные вкладки как
  master tabs. Явно разделять операции по `profileId`/`targetId`, не использовать
  master mapping для массового API и проверить сценарий при активном Sync.
- **Неполное закрытие:** CDP может создать blank target, но закрытие части
  исходных targets завершиться ошибкой. Возвращать фактический результат по
  каждому target и не закрывать blank target.
- **Частичное открытие ссылок:** не делать транзакцию всего запроса; продолжать
  обработку и возвращать детализацию ошибок.
- **Параллелизм:** ограничить число одновременно открытых CDP-сессий и закрывать
  их в `finally`.
- **Два WebSocket на браузер:** при активном Sync `CdpManager` уже держит
  соединение, а новый слой по умолчанию откроет второе. Chrome обычно допускает
  это, но целевой антидетект-браузер может иметь ограничения или нестабильное
  поведение. Обязательно проверить оба новых endpoint на целевом браузере при
  активном Sync. Если второе соединение вызывает сбои, рассмотреть
  переиспользование соединения `CdpManager` с подавлением `auto-attach` для
  пакетной операции, не нарушая существующий master/slave mapping.
- **Безопасность URL:** пользователь явно разрешил любые ссылки. Поэтому URL
  нельзя считать доверенным вводом для shell-команд или конкатенации JavaScript;
  передавать его только параметром CDP. Не логировать URL.
- **Совместимость:** существующие `/windows`, `/grid`, `/cascade`, `/focus` и
  API multi-control не менять по смыслу.

## Проверка

Из корня проекта:

```text
npm test
npm run lint
```

Сборка GUI:

```text
cd gui && npm run build
```

Ручная проверка с двумя или более running-профилями:

1. Открыть вкладку «Синхронизатор» и убедиться, что Sync отсутствует в Profiles.
2. Запустить Sync, выбрать Master и проверить обычную синхронизацию ввода.
3. Ввести несколько ссылок и открыть их; убедиться, что каждый running-профиль
   получил отдельную вкладку на каждую ссылку.
4. Нажать «Закрыть все вкладки»; убедиться, что в каждом профиле осталась одна
   новая пустая вкладка.
5. Остановить один профиль во время операции и убедиться, что остальные
   обработаны, а GUI показывает ошибку остановленного профиля.
6. Повторить операции при активном Sync и проверить отсутствие перепутанных
   target/mapping и продолжение обычной синхронизации.
7. Проверить работу при нуле running-профилей и при пустом поле ссылок.

## Критерии готовности

- `Window Arranger` переименован в «Синхронизатор» во всех UI-местах.
- Sync-контролы находятся только в синхронизаторе.
- Массовое открытие ссылок и закрытие вкладок работают для всех running-профилей.
- При частичных ошибках остальные профили/ссылки обрабатываются.
- Работа поверх активного Sync не ломает адресацию вкладок и mapping.
- URL не передаются через shell/склеенный JavaScript и не логируются.
- Unit-тесты, lint и GUI build проходят.
- БД, версия проекта и существующие API window-arranger/multi-control не
  изменены без необходимости.
