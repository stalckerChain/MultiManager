# TASK — Создание retry и duplicate run из Runs

## Цель

В разделе Automation → Runs добавить возможность создавать новые runs на основе
существующих. Оба результата должны быть отдельными `pending` runs, полностью
готовыми к запуску.

## Согласованное поведение

Для каждого run в списке доступны две кнопки независимо от статуса исходного
run (`pending`, `running`, `completed`, `partial`, `cancelled`):

1. **Создать новый run из невыполненных** — скопировать только задачи исходного
   run, у которых статус не равен `success`.
2. **Создать дубликат** — скопировать все задачи исходного run независимо от
   их статуса.

Для обеих операций:

- создаётся новый run со статусом `pending`;
- все новые `run_tasks` получают статус `pending`;
- не переносятся `exit_code`, `log_file_path`, `attempts`, `error_message`,
  `started_at`, `completed_at` и счётчики выполнения;
- исходный run и его задачи не изменяются;
- новый run не запускается автоматически;
- форма предварительно заполняется новым именем в том же формате, что и run,
  созданный из Matrix: `Run YYYY-MM-DD HH:mm`;
- пользователь может изменить имя;
- `parallel_limit` в форме по умолчанию равен `1` и может быть изменён
  пользователем; если значение отсутствует в API-запросе, использовать `1`.

Если у retry нет задач со статусом, отличным от `success`, вернуть ошибку `400`
и не создавать run. Если у исходного run нет задач, duplicate также должен
вернуть `400` без частично созданных данных.

## Backend API

Добавить в `src/api/runs.js` два endpoint-а:

- `POST /api/runs/:id/retry` — создать run из задач исходного run, не имеющих
  статус `success`;
- `POST /api/runs/:id/duplicate` — создать run из всех задач исходного run.

Тело запроса обоих endpoint-ов:

```json
{
  "name": "Новое имя",
  "parallel_limit": 1
}
```

Использовать существующую валидацию `runCreateSchema` либо расширить её без
изменения действующего контракта `POST /api/runs`. Если `parallel_limit` не
передан в запросе, использовать `1`.

Рекомендуемый успешный ответ: HTTP `201` с `run_id`, `tasks_created`, `name` и
сохранённым `parallel_limit`. Для отсутствующего исходного run вернуть `404`.
Для пустого набора задач вернуть `400` с отдельным информативным сообщением.

Создание run и копирование задач выполнить атомарно. Вынести минимальную
переиспользуемую операцию в существующие query-объекты `src/db/queries.js`, не
создавая новый service/factory/manager. При копировании брать снимок задач в
момент запроса, передавая только `project_name` и `profile_id`; новые значения
результата и времени должны оставаться пустыми.

Рекомендуемая структура query-операций:

- получить задачи исходного run с фильтром `status != 'success'` для retry;
- получить все задачи исходного run для duplicate;
- создать новый run с переданными настройками;
- batch-вставить выбранные пары в транзакции и обновить `total_tasks`.

Не менять схему БД, миграции, security-модель, версии проекта, `package.json` и
lock-файлы.

Запустить:

```bash
npm test -- --run tests/unit/runs-api.test.js tests/unit/queries-automation.test.js tests/unit/gui-automation-store.test.js
npm test
npm run lint
```

Обязательные тестовые сценарии:

1. Retry completed run копирует только `failed`/`pending` задачи и не копирует
   `success`.
2. Duplicate копирует все задачи любого статуса.
3. Все новые задачи имеют статус `pending` и очищенные runtime-поля.
4. Новый run имеет статус `pending`, правильные `total_tasks`, имя и
   `parallel_limit`.
5. Retry run без невыполненных задач возвращает `400`, исходные данные не
   меняются и новый run не появляется.
6. Duplicate run без задач возвращает `400` без частичного run.
7. Несуществующий исходный run возвращает `404`.
8. GUI store отправляет правильные URL и тела запросов.
9. Ручная проверка показывает обе кнопки для каждого статуса, позволяет
   изменить имя/лимит и оставляет созданный run pending до нажатия Start.

## Критерии приёмки

- Для каждого run доступны retry и duplicate независимо от его статуса.
- Retry содержит все задачи исходного run без статуса `success`.
- Duplicate содержит все задачи исходного run.
- Новые runs и задачи готовы к запуску и не наследуют результаты выполнения.
- Создание атомарно: не возникает run без полного набора задач при ошибке.
- Имя по умолчанию формируется по локальному времени пользователя как у run из
  Matrix и редактируется пользователем.
- Существующее создание run из Matrix и запуск pending run не регрессируют.
- API, GUI store, query-тесты, `npm test` и `npm run lint` проходят.

## Риски и ограничения

- Для `running` run retry использует снимок задач на момент HTTP-запроса. Статус
  исходных задач может измениться сразу после снимка; это ожидаемое поведение и
  не должно изменять исходный run.
- В текущей схеме `run_tasks` допускаются `pending`, `running`, `success`,
  `failed`; UI может отображать `cancelled`, но cancel-путь фактически переводит
  незавершённые задачи в `failed`. Фильтр retry должен использовать правило
  `status != 'success'`, чтобы не потерять любой будущий/дополнительный статус.
- Пары задач с удалённым профилем или проектом защищены существующими foreign
  keys/cascade; endpoint не должен обходить эти ограничения или создавать
  неполный run.
- Дубликат не переносит логи и ошибки: это сознательно, поскольку новый run
  должен стартовать как чистый.
