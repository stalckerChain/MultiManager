# TASK — Проверка и корректное завершение браузера в MM-automation

## Цель

Гарантировать, что браузер, запущенный через MultiManager для automation из
`stAuto0`, корректно завершается во всех основных сценариях:

- штатное завершение проекта из `main.py` в MM-режиме;
- ошибка проекта или другого участка выполнения;
- `KeyboardInterrupt`/остановка CLI;
- отмена automation-run через MultiManager;
- недоступность или ошибка MM API при завершении.

Штатный shutdown должен использовать существующую последовательность
MultiManager:

```text
POST /api/browser/:id/stop
  -> Browser.close через CDP
  -> ожидание exit
  -> graceful fallback
  -> force fallback только при необходимости
```

## Результат анализа

Обычный путь уже связан корректно:

```text
stAuto0/main.py
  -> BaseBrowser.close()
  -> MultiManagerClient.stop_browser()
  -> POST /api/browser/:id/stop
  -> src/api/browser.js: gracefulCloseBrowser()
```

Найдены незакрытые сценарии:

1. `stAuto0/main.py:372-383` в глобальных обработчиках
   `KeyboardInterrupt`, `SystemExit` и ошибок всегда вызывает
   `kill_chrome_processes()`. В MM-режиме это выполняет глобальный
   `taskkill /F /IM chrome.exe` и `taskkill /F /IM node.exe`, обходя graceful
   shutdown и потенциально завершая сам MultiManager.
2. `src/executor/index.js:276-288` в `RunExecutor.cancel()` принудительно
   завершает Python-процессы. При этом `finally` в `main.py` может не
   выполниться, а браузер, запущенный через MM, останется работать.
3. Текущие тесты проверяют прямой вызов `BaseBrowser.close()`, но не проверяют
   полный CLI-flow `main.py` и отмену automation-run.
4. `BaseBrowser.close()` логирует ошибку `stop_browser()` и продолжает только
   локальное закрытие Playwright-сессии. Нужно проверить и явно зафиксировать
   поведение при недоступности MM API, не создавая неконтролируемый orphan
   Chromium.

## Согласованное решение

1. Сохранить существующую graceful shutdown-логику MultiManager без изменения
   API endpoint-ов, CDP-протокола, схемы БД и таймаутов.
2. В `stAuto0` выполнять глобальный legacy cleanup только в legacy-режиме.
   MM-режим не должен выполнять глобальный `taskkill`; остановка профиля должна
   проходить через `POST /api/browser/:id/stop`.
3. При отмене automation сначала инициировать остановку браузеров профилей
   через существующий lifecycle MultiManager, затем завершать Python-процессы.
   Реализацию выполнить через существующие `RunExecutor`/`runs` без нового
   архитектурного слоя.
4. Сохранить текущий legacy-путь: при запуске без MultiManager аварийное
   завершение по-прежнему использует legacy cleanup.
5. Не логировать токены, пароли, cookies, сид-фразы или proxy credentials.

1. В MultiManager выполнить точечные тесты затронутых executor/browser

2. Выполнить `npm test` в MultiManager.
3. В stAuto0 выполнить `python -m pytest tests/ -v`.
4. На Windows запустить реальный MM Core и automation из GUI/Run API, дождаться

5. На Windows запустить `python main.py` в MM-режиме и проверить, что после

6. Повторить проверку с ошибкой проекта и с `Ctrl+C`; убедиться, что первым

7. Отменить активный automation-run через API и проверить отсутствие

8. Проверить legacy-запуск отдельно: его существующий cleanup не должен быть

## Критерии приёмки

- В MM-режиме штатное, ошибочное и отменённое завершение не оставляет браузер
  запущенным.
- `Browser.close`/graceful shutdown MultiManager остаётся первым способом
  остановки, а force kill используется только после таймаутов.
- `stAuto0` в MM-режиме не выполняет глобальный `taskkill /F`.
- Отмена run не оставляет orphan Chromium после принудительного завершения
  Python child.
- Legacy-режим сохраняет прежнее поведение.
- Все существующие тесты MultiManager и stAuto0 проходят.
- API-ответы, схема БД, зависимости и версия проекта не изменены.

## Риски и ограничения

- Если MM Core недоступен, stAuto0 не может гарантировать удалённую остановку
  профиля; это должно быть отражено в логе и статусе, но не должно приводить к
  глобальному уничтожению чужих процессов.
- `child.kill()` на Windows может завершить Python без выполнения `finally`,
  поэтому остановка браузера при cancel должна инициироваться со стороны
  MultiManager до убийства child.
- Одновременный штатный `close()` из stAuto0 и cancel из MultiManager требует
  сохранения защиты `stoppingProfiles`.
- Реальная проверка flush WAL/cookies возможна только на Windows с конкретной
  сборкой Chromium; unit-тесты подтверждают порядок вызовов, но не заменяют
  smoke-тест.

## Ограничения реализации

- Изменять только lifecycle браузера, отмену automation и связанные тесты/
  документацию.
- Не менять `package.json`, lock-файлы и версию проекта.
- Не добавлять новые зависимости.
- Не менять публичные API-контракты endpoint-ов.
- После каждого завершённого пункта реализации отметить соответствующий пункт
  плана как выполненный.
