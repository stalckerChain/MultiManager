# TASK — Сохранение сгенерированного fingerprint профиля

## Цель

Исправить редактирование профиля: после нажатия `Generate Fingerprint` новый
полный fingerprint должен оставаться в форме и сохраняться в БД по кнопке `OK`.
При следующем запуске профиля CloakBrowser должен получить новый сохранённый
`fingerprint_seed`.

## Согласованные требования

- `Generate Fingerprint` генерирует новый fingerprint для текущей платформы.
- До нажатия `OK` изменения не записываются в БД; отмена формы не меняет профиль.
- В форму должны попасть как минимум `fingerprint_seed`, `user_agent`,
  `screen_resolution`, `hardware_cores` и `hardware_memory`.
- При `OK` все эти поля сохраняются одной операцией обновления профиля.
- Если платформа изменилась и пользователь не нажал `Generate Fingerprint`,
  сохранить существующее поведение: backend автоматически генерирует новый
  fingerprint для новой платформы.
- Если пользователь нажал `Generate Fingerprint`, при сохранении нельзя
  генерировать второй случайный fingerprint: нужно сохранить подготовленный
  формой seed и связанные с ним параметры.
- Схему БД и формат существующих профилей не менять: необходимые колонки уже
  существуют.
- CloakBrowser должен продолжить получать seed через существующий аргумент
  `--fingerprint=<profile.fingerprint_seed>`.
- Не изменять версию проекта и changelog.

## Архитектурное решение

Использовать существующий endpoint `POST /api/fingerprint/generate` как источник
полного fingerprint. В `ProfileModal.vue` добавить fingerprint-поля в состояние
формы, при генерации присваивать их из ответа API, а при сохранении отправлять
их вместе с остальными значениями профиля.

В `src/api/validate.js` расширить `profileUpdateSchema` полями fingerprint с
проверкой типов и UUID-формата для seed. В `src/api/profiles.js` различать два
случая:

1. В запросе передан подготовленный fingerprint: использовать значения из
   `body`, а не генерировать новый fingerprint только потому, что изменилась
   платформа; валидировать согласованность его платформы с выбранной платформой
   и передать значения в существующий query update.
2. Fingerprint не передан, но платформа отличается от сохранённой: сохранить
   текущую автоматическую генерацию полного fingerprint для новой платформы.

Если платформа не менялась и fingerprint не передан, сохранить старые
fingerprint-значения. Не принимать значения `user_agent` или hardware отдельно
от seed так, чтобы можно было случайно получить несогласованный набор.

В `src/db/queries.js` использовать существующие поля обновления и не добавлять
новый слой, сервис или миграцию. Обновление должно быть атомарным на уровне
одного SQL `UPDATE`; `COALESCE` не должен препятствовать сохранению переданного
seed и нулевых/положительных hardware-значений.

## План реализации

### 1. Состояние и форма GUI

- `gui/src/renderer/views/ProfileModal.vue`:
  - добавить в `form` поля `fingerprint_seed`, `hardware_cores` и
    `hardware_memory`;
  - при открытии существующего профиля загружать эти поля;
  - при создании нового профиля сбрасывать их вместе с остальными полями;
  - в `generateFingerprint()` присваивать из ответа API seed, User-Agent,
    resolution и hardware-параметры;
  - при `handleOk()` передавать fingerprint-поля в событии `save`;
  - не записывать сгенерированные значения в backend до подтверждения `OK`.

### 2. Контракт обновления профиля

- `src/api/validate.js`:
  - добавить в `profileUpdateSchema` поля `fingerprint_seed`,
    `user_agent`, `screen_resolution`, `hardware_cores`,
    `hardware_memory`;
  - ограничить типы и разумные значения hardware-полей;
  - проверить формат `fingerprint_seed` как UUID;
  - не разрешать частичный fingerprint-набор без явного решения в коде.

  Для согласованности платформы использовать один из следующих проверяемых
  вариантов без доверия к произвольным клиентским данным:

  - добавить в payload отдельное поле `fingerprint_platform` и сравнивать его
    с `platform`, одновременно проверяя, что оно входит в enum поддерживаемых
    платформ;
  - либо определить платформу по `user_agent` и сверить её с `platform` по
    тем же правилам, что используются генератором (`Windows NT` для Windows,
    `Macintosh` для macOS, `X11; Linux` для Linux).

  Предпочтительный вариант — передавать `fingerprint_platform` явно: это не
  требует хрупкого разбора User-Agent. При несовпадении возвращать `400` и не
  выполнять обновление.

- `src/api/profiles.js`:
  - извлечь fingerprint-поля из проверенного тела запроса;
  - при переданном наборе использовать его при `queries.update()`;
  - при изменении платформы без переданного набора оставить автоматическую
    генерацию через `generateFingerprint()`;
  - не перегенерировать fingerprint, если он уже был подготовлен кнопкой;
  - вернуть обновлённый профиль с новым seed.

- `src/db/queries.js`:
  - проверить, что существующий update действительно сохраняет переданные
    seed, User-Agent, resolution, cores и memory;
  - для `hardware_cores` и `hardware_memory` передавать значение по проверке
    `value !== undefined ? value : null`, а не через `value || null`, чтобы не
    терять явные нулевые значения (при этом schema должна отдельно решить,
    разрешены ли нулевые значения);
  - при необходимости минимально скорректировать параметры update, не меняя
    схему БД и не затрагивая остальные поля профиля.

### 3. Тесты

- `tests/unit/internal-profiles.test.js` или существующий подходящий unit-тест:
  - проверить обновление профиля с переданным fingerprint-набором;
  - проверить, что seed и связанные поля сохраняются.

- `tests/integration/api-real.test.js` или подходящий API-тест:
  - сгенерировать fingerprint;
  - отправить его в `PUT /api/profiles/:id`;
  - проверить, что новый seed возвращается и сохраняется после повторного GET;
  - проверить сценарий смены платформы без явного fingerprint;
  - проверить, что при переданном fingerprint backend не генерирует второй
    seed.

- При наличии тестов GUI для `ProfileModal.vue` добавить проверку, что ответ
  `Generate Fingerprint` попадает в payload события `save`.

## Проверка результата

1. Выполнить `npm test`.
2. Проверить API-сценарий: старый seed отличается от сгенерированного после
   `Generate Fingerprint` + `OK` и остаётся таким после повторного GET.
3. Проверить запуск профиля и наличие сохранённого seed в аргументе
   `--fingerprint=`.
4. Проверить отмену формы: после Generate и Cancel данные профиля в БД не
   изменились.
5. Проверить смену платформы без Generate: backend создаёт новый корректный
   fingerprint для новой платформы.
6. Проверить, что обычное редактирование имени, proxy, тегов и аккаунтов не
   сбрасывает fingerprint-поля.

## Риски и ограничения

- Seed является частью идентичности fingerprint для CloakBrowser. Нельзя
  сохранять новый seed вместе со старыми hardware-параметрами из-за частичного
  payload.
- Переданный GUI seed должен проверяться backend, поскольку клиент нельзя
  считать доверенным источником.
- При работающем профиле изменение fingerprint применяется только при
  следующем запуске, если CloakBrowser не поддерживает динамическую смену
  startup-аргументов. Останавливать профиль автоматически не требуется.
- Миграция БД не нужна: `fingerprint_seed`, `user_agent`,
  `screen_resolution`, `hardware_cores` и `hardware_memory` уже присутствуют в
  таблице `profiles`.
- Дополнительные поля ответа генератора (`navigator_platform`, `color_depth`,
  `webgl_renderer`) не сохранять в БД без отдельного требования и миграции.
