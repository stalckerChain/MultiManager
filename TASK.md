# TASK — Жизненный цикл Electron, single instance и tray

## Цель

Исправить поведение Windows-приложения MultiManager:

- повторный запуск не должен создавать второй Electron-процесс и второй backend;
- повторный запуск должен активировать уже запущенное окно;
- обычный клик по иконке в системном трее должен показывать и фокусировать окно;
- закрытие крестиком должно сохранить текущую модель сворачивания в трей;
- пункт «Выход» должен полностью завершать GUI и backend;
- в трее должна отображаться настоящая иконка приложения, а не пустой квадрат.

## Согласованные решения

1. Сохранить текущую семантику крестика: обработчик `BrowserWindow.close` отменяет закрытие и скрывает окно, если приложение не выходит через явную команду завершения.
2. Для защиты от нескольких экземпляров использовать `app.requestSingleInstanceLock()`.
3. Если lock не получен, второй процесс должен завершиться. Первый процесс по событию `second-instance` должен показать, восстановить при необходимости и сфокусировать главное окно.
4. Обработать обычный клик tray-иконки так же, как существующий пункт «Открыть панель» и двойной клик.
5. Исправить разрешение пути к tray-ресурсам так, чтобы dev-режим и packaged-режим находили файлы, включённые в `app.asar/resources`.
6. Не менять backend API, схему БД, модель авторизации и версию проекта.

## Текущее состояние и причины

- `gui/src/main/index.js:166-172` отменяет закрытие окна и вызывает `hide()`, поэтому backend остаётся запущенным до явного выхода.
- `gui/src/main/index.js` не вызывает `app.requestSingleInstanceLock()` и не обрабатывает `second-instance`; повторный запуск создаёт новый Electron-процесс.
- `gui/src/main/tray.js:64-67` подписан только на `double-click`; обычный клик не восстанавливает окно.
- `gui/src/main/tray.js:7-14` в packaged-режиме строит путь через `process.resourcesPath/resources`. При текущей конфигурации `files: ["resources/**/*"]` иконки находятся внутри `app.asar/resources`, поэтому путь может вести к отсутствующему файлу. При пустом изображении код явно создаёт `nativeImage.createEmpty()`.
- Существующие ресурсы `gui/resources/tray-icon.ico` и `gui/resources/tray-icon.png` присутствуют; заменять графические файлы без отдельной необходимости не нужно.
- Тестов Electron lifecycle/tray/single-instance в репозитории не найдено. Поведение потребуется покрыть доступными unit-проверками и ручной проверкой packaged Windows-сборки.

## План реализации

### 1. Защитить приложение от второго экземпляра

Затрагиваемый файл: `gui/src/main/index.js`.

1. Получить single-instance lock до регистрации запуска окна и до `app.whenReady()`.
2. Если lock не получен, вызвать корректное завершение текущего второго процесса и не запускать backend, окно или tray.
3. Для первого процесса зарегистрировать `app.on('second-instance', ...)`.
4. В обработчике проверить существование главного окна, вызвать `restore()` для минимизированного окна, затем `show()` и `focus()`.
5. Не использовать IPC или сетевой endpoint для этой задачи: механизм Electron сам передаёт событие первому экземпляру.
6. Учесть гонку раннего повторного запуска: обработчик не должен падать, если главное окно ещё не создано; после создания окно должно оставаться доступным для последующей активации.

### 2. Восстановить окно из tray

Затрагиваемые файлы: `gui/src/main/tray.js`, при необходимости `gui/src/main/index.js`.

1. Вынести или локально определить единое действие `show/restore/focus`, чтобы контекстное меню, двойной и обычный клик использовали одинаковое поведение.
2. Подписать tray на событие `click` и показывать главное окно при обычном клике.
3. Сохранить существующие пункты контекстного меню и двойной клик.
4. Не вызывать `startCore()` при восстановлении окна: уже работающий backend должен использоваться повторно.
5. Перед показом проверить, что `mainWindow` существует и не уничтожен.

### 3. Исправить путь tray-иконки

Затрагиваемый файл: `gui/src/main/tray.js`.

1. Согласовать путь с фактической конфигурацией `gui/package.json`: ресурсы приложения находятся относительно `__dirname` внутри `app.asar`.
2. Сохранить выбор ICO для Windows и PNG для остальных платформ.
3. Сохранить fallback на альтернативный формат, но не маскировать ошибку пустой иконкой без диагностируемой проверки пути.
4. Проверить фактическое размещение ресурсов по секции `build.files` в `gui/package.json` и результату electron-builder, не ориентируясь только на комментарии в `DEPLOY.md`.
5. Перед созданием `Tray` проверить, что `nativeImage` не пустой.
6. При пустой иконке записать в лог путь выбранного файла, факт его существования, выбранный формат и причину fallback; не логировать секреты или лишние пользовательские данные.
7. Не менять `gui/package.json` и не добавлять новую зависимость, если проверка подтверждает корректность текущей конфигурации.

### 4. Добавить тестовое покрытие

Затрагиваемые файлы: новый или существующий unit-тест в `tests/unit/`, предпочтительно отдельный тест для Electron lifecycle/tray.

1. Проверить статически или через минимальные моки, что main process использует `requestSingleInstanceLock()` и прекращает запуск второго экземпляра при отрицательном результате.
2. Проверить обработку события `second-instance`: вызвать `restore()` только если окно действительно минимизировано, затем показать и сфокусировать существующее окно.
3. Проверить, что tray подключает обработчик обычного клика и вызывает условное восстановление, показ и focus окна.
4. Проверить выбор корректного ресурса и fallback между ICO/PNG без реального запуска GUI, если Electron API замокать можно надёжно.
5. Не запускать backend и не создавать реальные системные tray-объекты в unit-тестах.
6. Отказаться от хрупких Electron-моков, если тест зависит от внутренних деталей Electron, требует сложной имитации системного Tray/BrowserWindow, нестабилен между версиями Electron или проверяет только порядок вызовов вместо пользовательского поведения.
7. В этом случае оставить детерминированные unit-проверки чистых вспомогательных функций/условий и обязательную ручную runtime-проверку на Windows packaged-сборке; отсутствие полного мока явно зафиксировать в отчёте проверки.

### 5. Проверить результат

1. Запустить `npm test`.
2. Запустить GUI в dev-режиме, закрыть окно крестиком и убедиться, что оно скрывается, а backend остаётся доступным.
3. Нажать обычным кликом tray-иконку и убедиться, что открывается существующее окно.
4. Запустить приложение повторно через ярлык/EXE и убедиться, что нового окна и второго backend-процесса нет, а первое окно активируется.
5. Проверить отдельно минимизированное и просто скрытое окно: `restore()` вызывается только для минимизированного, оба состояния затем показываются и фокусируются.
6. Проверить пункт «Выход»: backend завершается, tray исчезает, повторный запуск после этого создаёт один новый экземпляр.
7. Собрать Windows packaged-версию командой `cd gui && npm run build` либо выполнить доступную эквивалентную сборку.
8. В packaged-версии проверить отображение tray-иконки, обычный клик, двойной клик, контекстное меню и повторный запуск.
9. Проверить логи на отсутствие повторного запуска backend при активации существующего экземпляра.
10. Не менять версии, release-файлы, backend API или security-модель.

## Ограничения и риски

- Не завершать backend при обычном крестике: это противоречит текущей модели сворачивания в трей и согласованному решению.
- Между запуском второго экземпляра и созданием первого окна возможен короткий период, когда `second-instance` ещё не может показать окно; обработчик должен быть безопасным при `null`.
- Single-instance lock действует в пределах одного пользователя/окружения Electron; отдельные ручные запуски backend не контролируются этим механизмом.
- Tray API платформозависим, поэтому основной runtime-сценарий нужно проверить на Windows packaged-сборке.
- Путь к иконке должен быть проверен и в dev, и после упаковки; нельзя считать успешную dev-проверку достаточной.
- При проблеме с иконкой логи должны позволять определить отсутствие файла, неверный путь или пустой результат `nativeImage` без повторной сборки наугад.
- Electron-моки считаются необязательными, если они становятся version-sensitive или проверяют реализацию вместо результата; тогда обязательны чистые unit-проверки и Windows runtime-проверка.
- Не добавлять новую зависимость и не изменять версию проекта.

## Критерии готовности

- Второй запуск не создаёт второй GUI или backend-процесс.
- Второй запуск активирует первое окно.
- Обычный клик по tray-иконке восстанавливает и фокусирует окно.
- Крестик скрывает окно, не завершая backend.
- «Выход» завершает backend и GUI.
- В packaged Windows-версии отображается `tray-icon.ico` или корректный fallback.
- `npm test` проходит.
- Ручная проверка packaged-сборки подтверждает все tray/single-instance сценарии.
