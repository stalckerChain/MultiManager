# TASK — Синхронизация каталога профилей между MultiManager и stAuto0

## Цель

Исправить `stAuto0/scripts/migrate_profile_dirs.py`, который сейчас копирует профили в устаревший каталог `CloakManager/profiles`.

Скрипт должен получать фактический каталог профилей у запущенного MultiManager через авторизованный HTTP API. Это необходимо, потому что фактический каталог зависит не только от стандартного `%APPDATA%/MultiManager`, но и от переменной окружения `MULTIMANAGER_DATA_DIR`.

После реализации данные должны копироваться в:

```text
<каталог данных MultiManager>/profiles/<profile UUID>/BrowserData
```

Нельзя оставлять автоматический fallback на `CloakManager`: при недоступности MM скрипт должен завершаться с понятной ошибкой, а не создавать копию данных в неправильном каталоге.

## Согласованное решение

Добавить в MultiManager внутренний endpoint:

```text
GET /api/internal/profile-storage
```

Endpoint возвращает каталог, в котором хранятся стандартные профили MultiManager:

```json
{
  "profiles_dir": "C:\\Users\\stalcker\\AppData\\Roaming\\MultiManager\\profiles"
}
```

Endpoint не принимает параметры, не изменяет состояние и не обращается к БД. Он должен вычислять путь через существующий `getDataDir()` и возвращать `path.join(getDataDir(), 'profiles')`.

Все API-запросы уже проходят через общий `authMiddleware` в `src/core/app.js`. Дополнительную или отдельную схему авторизации для endpoint добавлять нельзя.

## Важные ограничения

- Не изменять схему БД и миграции БД.
- Не менять существующие API профилей.
- Не менять формат `mapping.json`.
- Не возвращать токены, master key, пароли или другие секреты.
- Не логировать полный Bearer-токен.
- Не использовать `CloakManager` ни как основной путь, ни как fallback.
- Не создавать новый сервис, provider или отдельный менеджер путей.
- Не менять номер версии в `package.json`, `CHANGELOG.md` или других файлах версии.
- Не менять поведение копирования профиля: каталог `Default/Extensions` по-прежнему должен исключаться.
- Не удалять существующие пользовательские изменения в рабочем дереве.

## Часть 1. Изменения в MultiManager

### 1.1. Реализовать endpoint

Файл:

```text
MultiManager/src/api/internal.js
```

Добавить `GET /profile-storage` относительно уже смонтированного `/api/internal`. Итоговый URL должен быть именно `/api/internal/profile-storage`.

Алгоритм endpoint:

1. Вызвать существующий `getDataDir()` из `src/core/data-dir.js`.
2. Построить путь через `path.join(getDataDir(), 'profiles')`.
3. Вернуть HTTP 200 и JSON `{ profiles_dir: <absolute path> }`.
4. Не проверять существование каталога и не создавать его. Создание целевых подкаталогов выполняет операция копирования профиля.
5. Не принимать `profile_id` и не вычислять путь из пользовательского значения.
6. Не добавлять отдельный middleware авторизации: общий `authMiddleware` уже применяется до роутеров в `src/core/app.js`.
7. Добавить `logger.info(...)` по аналогии с существующими internal endpoint в этом файле. Лог должен подтверждать вызов endpoint и факт выдачи каталога, но не должен содержать Bearer-токен или другие секреты. Полный абсолютный путь допустимо логировать, если это соответствует текущему стилю логирования internal API.

Путь должен отражать текущую конфигурацию процесса MM:

- без `MULTIMANAGER_DATA_DIR`: `%APPDATA%/MultiManager/profiles` на Windows;
- с `MULTIMANAGER_DATA_DIR=/absolute/custom/path`: `/absolute/custom/path/profiles`;
- аналогично для Linux/macOS через существующую реализацию `getDataDir()`.

Если `getDataDir()` выбрасывает ошибку из-за некорректного `MULTIMANAGER_DATA_DIR`, не перехватывать её в endpoint как успешный ответ. Общий обработчик ошибок должен вернуть обычную ошибку сервера без stack trace клиенту.

4. Некорректный относительный `MULTIMANAGER_DATA_DIR` приводит к ошибке сервера. С учётом тестового error handler в `internal-profiles.test.js` (строки 143-146) проверить одновременно, что ответ содержит понятное сообщение об ошибке, связанное с требованием абсолютного пути, и не содержит поле или текст stack trace.

Тесты должны сохранять и восстанавливать `APPDATA`, `MULTIMANAGER_DATA_DIR` и состояние временной базы так же, как уже сделано в этом файле. Не использовать реальный пользовательский каталог.

Если текущая тестовая обвязка вызывает router напрямую без `authMiddleware`, endpoint должен тестироваться так же, как остальные маршруты этого файла. Отдельный тест общей Bearer-аутентификации для этого endpoint не нужен, потому что авторизация проверяется в `src/core/app.js` и покрывается существующими auth-тестами.

## Часть 2. Изменения в stAuto0

### 2.1. Расширить HTTP-клиент MultiManager

Файл:

```text
stAuto0/Core/multimanager.py
```

Добавить в `MultiManagerClient` метод примерно следующего назначения:

```python
async def get_profile_storage_dir(self) -> str:
    ...
```

Требования к методу:

1. Выполнять `GET /api/internal/profile-storage` через существующий `_request`.
2. Использовать существующие заголовки Bearer и текущую логику `MultiManagerClient`.
3. Использовать короткий timeout, аналогичный `get_zerion_extension_id` (3 секунды).
4. Для HTTP-статуса `>= 400` выбрасывать информативную ошибку через существующий `_check_response` или эквивалентную логику.
5. Проверять, что JSON является объектом.
6. Проверять, что `profiles_dir` является непустой строкой.
7. Проверять, что `profiles_dir` является абсолютным путём средствами Python (`os.path.isabs`).
8. При невалидном JSON, отсутствующем поле, пустой строке или относительном пути выбрасывать `RuntimeError` с понятным сообщением.
9. Не логировать токен и не включать его в текст исключения.
10. Не подставлять `CloakManager` при любой ошибке.

Метод должен корректно работать как внутри `async with MultiManagerClient(...)`, так и с текущим ленивым созданием session, принятом в клиенте.

### 2.2. Изменить скрипт миграции каталогов

Файл:

```text
stAuto0/scripts/migrate_profile_dirs.py
```

Изменения:

1. Удалить функцию `get_target_base()`, которая вычисляет путь через `APPDATA/CloakManager`.
2. Удалить все fallback-строки и сообщения, содержащие `CloakManager`.
3. Импортировать существующие `MultiManagerClient` и `detect_mm` из `Core.multimanager`.
4. Сделать получение target base частью асинхронного сценария `main()`.
5. Добавить CLI-аргументы, совместимые с `scripts/migrate_to_sqlite.py`:
   - `--token` — Bearer-токен MM, по умолчанию `None`;
   - `--port` — порт MM, по умолчанию `3000`;
   - `--host` — сохранить для совместимости интерфейса, по умолчанию `127.0.0.1`.
6. Получить настройки и доступность MM через существующий `detect_mm(port=args.port, token=args.token)` либо согласованную с ним минимальную интеграцию.
7. Если MM недоступен, вывести ошибку с адресом подключения и завершиться с ненулевым кодом до начала копирования.
8. Открыть `async with MultiManagerClient(port=port, token=token) as mm`.
9. Внутри этого контекста вызвать `await mm.get_profile_storage_dir()` один раз до цикла копирования.
10. Использовать полученный путь как `target_base`.
11. Для каждой записи оставить целевой путь строго таким:
    `os.path.join(target_base, uuid, 'BrowserData')`.
12. До копирования не нужно вручную создавать `target_base`: `shutil.copytree(..., dirs_exist_ok=True)` создаёт нужные каталоги.
13. Если endpoint недоступен, вернул ошибку или невалидный путь, завершить миграцию с ненулевым кодом и не копировать ни одного профиля.
14. Сохранить текущую обработку ошибок отдельных профилей, `--overwrite`, фильтрацию аккаунтов, подсчёт файлов и итоговую статистику.
15. Обновить логирование: явно вывести фактический target base, но не выводить токен.
16. Не записывать `profiles_dir` в `mapping.json` и не добавлять его в БД.

Предпочтительно получить каталог MM до чтения/копирования профилей, чтобы ошибка конфигурации обнаруживалась до частичной миграции. Текущая проверка `mapping.json` и фильтрация аккаунтов должна остаться до цикла, но не должна скрывать ошибку подключения к MM.

## Совместимость и безопасность

- Endpoint должен работать только через уже существующую Bearer-аутентификацию MM.
- Не добавлять обход авторизации для localhost.
- Не передавать токен в query string.
- Не возвращать путь из пользовательского запроса или из произвольного query-параметра.
- Не добавлять запись полного пути или токена в логи, если это не требуется текущим стилем логирования. Допустима запись target base в локальный лог миграции, так как это не секрет, но токен и credentials должны быть исключены.
- Ошибка должна быть остановочной до копирования, чтобы не получить частично перенесённые профили из-за неправильной конфигурации.
- Endpoint не должен зависеть от наличия конкретного профиля или UUID.
- Тесты не должны читать или удалять реальные каталоги пользователя.
