# TASK — Graceful shutdown Chromium через CDP

## Цель

Перед сигнальным завершением Chromium отправлять CDP-команду
`Browser.close()`, чтобы браузер сам корректно закрыл вкладки и сбросил
persistent storage, включая WAL-журналы SQLite (`Cookies`, Local Storage и
связанные данные).

## Подтверждённая проблема

`src/api/browser.js` сейчас в `gracefulCloseBrowser()` сразу вызывает
`tree-kill(child.pid, 'SIGTERM')`. В Windows-ветке `tree-kill` фактически
выполняет `taskkill /pid <pid> /T /F` независимо от переданного сигнала.
Это принудительное завершение и не является graceful shutdown для Chromium.

В проекте уже есть:

- CDP-порт профиля в `cdpPorts` внутри `src/api/browser.js`;
- browser-level CDP-клиент `src/cdp/client.js`;
- таймаут ожидания завершения `SHUTDOWN_TIMEOUT_MS = 8000`;
- единая функция shutdown, используемая endpoint-ами `POST /:id/stop` и
  `POST /shutdown`.

## Согласованные требования

- Первым действием shutdown после установки обработчика `exit` должна быть
  попытка CDP `Browser.close`.
- CDP-вызов выполнять на browser-level WebSocket, без
  `Target.attachToTarget` и без `sessionId`.
- WebSocket закрывать в `finally`.
- Ошибка, отсутствие CDP-порта или недоступность CDP не должны препятствовать
  fallback-завершению процесса.
- Исключить из warning ожидаемые сообщения закрытого WebSocket из CDP-клиента:
  `WebSocket was closed` и `Connection closed` (включая эквивалентное
  сообщение с тем же смыслом), возникающие после принятия Chromium команды
  `Browser.close`.
- После CDP-попытки ждать `exit` процесса до 8 секунд.
- Использовать отдельные таймауты фаз: CDP close — 2 секунды, ожидание
  завершения после CDP — 8 секунд, signal fallback — 5 секунд.
- При таймауте использовать graceful-сигнал:
  - Unix: `tree-kill(pid, 'SIGTERM')`;
  - Windows: `taskkill /PID <pid> /T` без `/F`.
- Если процесс после сигнального fallback не завершился, использовать force:
  - Unix: `tree-kill(pid, 'SIGKILL')`;
  - Windows: `taskkill /PID <pid> /T /F`.
- Не менять API-ответы endpoint-ов, схему БД, зависимости и версию проекта.
- Не логировать cookies, токены, пароли или содержимое пользовательских данных.
- Защитить stop/shutdown от повторного запуска для одного профиля через
  отдельную `Map` `stoppingProfiles`, по аналогии с `runningProfiles`.

## Архитектурное решение

Расширить существующую `gracefulCloseBrowser`, если это сохраняет читаемость,
не вводя новый менеджер процессов, отдельный архитектурный слой или набор
избыточных helper-функций.

1. В начале `gracefulCloseBrowser` получить CDP-порт из `cdpPorts`, до любых
   операций, которые могут привести к cleanup и удалить порт.
2. Зарегистрировать `exit` до начала shutdown-команд, чтобы не пропустить
   быстрый выход Chromium.
3. При наличии порта подключиться через существующий `cdpClient` к
   browser-level endpoint `ws://127.0.0.1:<port>/devtools/browser`.
4. Отправить `Browser.close` без session ID в пределах CDP timeout 2 секунды.
   Не требовать обязательного ответа:
   Chromium может закрыть WebSocket сразу после принятия команды.
5. В `finally` закрыть WebSocket. Ошибку записать как warning и продолжить
   fallback, кроме ожидаемых сообщений `WebSocket was closed` и `Connection
   closed` (или эквивалентных сообщений), которые не должны логироваться как
   warning.
6. После CDP-попытки ждать `exit` до 8 секунд.
7. При таймауте выполнить платформенный graceful fallback и ждать его результат
   до 5 секунд.
8. На Windows после `taskkill /PID <pid> /T` без `/F` всегда ждать короткий
   фиксированный интервал 2–3 секунды, затем переходить к force kill. Не ждать
   полный signal timeout на Windows.
9. После дополнительного ожидания выполнить платформенный force fallback и
   завершить Promise независимо от результата команды, записав ошибку в лог.

Для вызова Windows-команд использовать безопасный API запуска процесса с
числовым PID, а не конкатенацию пользовательского ввода в shell-команду.
Проверить, что graceful-команда Windows не содержит `/F`, а force-команда
содержит `/F`.

## Проверка результата

1. Выполнить точечный тест `npx vitest run tests/unit/browser-shutdown.test.js`.
2. Выполнить полный набор `npm test`.
3. На Windows проверить реальный останов запущенного Chromium и убедиться,
   что первой командой не является принудительный `taskkill /F`.
4. На Windows всегда выдержать короткое ожидание 2–3 секунды после
   `taskkill /PID <pid> /T` без `/F`, затем выполнить force kill. Зафиксировать
   в документации, что WM_CLOSE может игнорироваться Chromium.
5. Проверить сценарий недоступного CDP: процесс всё равно завершается через
   fallback и shutdown не зависает дольше ожидаемого лимита.
6. Проверить сценарий успешного CDP-закрытия: сигнальный fallback не вызывается.
7. Отправить два stop-запроса одновременно и убедиться, что второй не запускает
   повторное завершение того же child.
8. После остановки и повторного запуска проверить сохранение cookies и Local
   Storage на профиле с изменениями, достаточными для появления WAL-записей.

## Риски и ограничения

- `Browser.close` может закрыть WebSocket до ответа CDP; отсутствие ответа не
  должно ошибочно считаться причиной пропуска graceful shutdown, если команда
  была отправлена.
- Недоступный CDP, битый порт или уже завершившийся процесс должны приводить к
  быстрому fallback, а не к ожиданию полного CDP timeout плюс полного process
  timeout без контроля.
- `tree-kill` на Windows нельзя использовать для различения graceful и force
  режимов: его Windows-реализация всегда добавляет `/F`.
- `taskkill` без `/F` зависит от поведения GUI-процесса Chromium; после
  фиксированного ожидания 2–3 секунды выполняется force kill. Возможное
  игнорирование WM_CLOSE нужно явно описать в документации.
- Параллельные вызовы stop/shutdown для одного профиля могут привести к двум
  shutdown-последовательностям. `stoppingProfiles` должен исключить повторный
  shutdown.
- Сохранность WAL и пользовательских данных подтверждается только реальным
  тестом на Windows с конкретной сборкой Chromium; unit-тесты подтверждают
  порядок и fallback, но не гарантируют flush данных браузером.
