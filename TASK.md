# TASK — Нормализация и проверка дубликатов прокси при обновлении

## Цель

Исправить сохранение прокси так, чтобы `host` нормализовался перед сравнением
и записью, а `PUT /api/proxies/:id` не позволял создать дубликат существующего
`host:port`. Поведение дубликата для `POST` и `PUT` должно быть одинаковым:
HTTP `409 CONFLICT` с текущим сообщением.

## Согласованные требования

- Нормализация `host`: удалить начальные/конечные пробелы через `trim()` и
  привести значение к нижнему регистру через `toLowerCase()`.
- В БД сохраняется уже нормализованный `host`.
- Дубликат определяется по нормализованной паре `host + port`.
- `type`, `username`, `password` и `proxy_rotation_url` не входят в ключ
  дубликата.
- `POST /api/proxies` сохраняет только нормализованный host и проверяет дубль
  по нормализованным значениям.
- `POST /api/proxies/import` применяет ту же нормализацию и дедупликацию, в том
  числе между строками одного импорта.
- `PUT /api/proxies/:id` проверяет конфликт с другой записью до изменения.
- В `PUT` нормализация применяется только если поле `host` фактически передано
  в запросе. Если `host` отсутствует, сохраняется текущее значение через
  существующую partial/COALESCE-семантику.
- Обновление той же записи на ее текущий нормализованный `host:port` допустимо.
- При конфликте `PUT` возвращает HTTP `409` с тем же сообщением:
  `Прокси с таким host:port уже существует`.
- Схему БД и существующие API-коды контрактов менять не нужно.
- Обновить русскую, английскую и китайскую API-документацию, а также описание
  базы данных.

## Архитектурное решение

Использовать существующий слой proxy queries и текущую проверку
`findByHostPort`. Изменить SQL проверки так, чтобы она находила также старые
ненормализованные записи:

```sql
WHERE LOWER(TRIM(host)) = ? AND port = ?
```

Параметром передавать уже нормализованный host. Добавить одну переиспользуемую
нормализацию host в подходящем
существующем модуле, не создавая новый сервис или класс.

Проверку `PUT` выполнять до `queries.update`: найти запись по нормализованному
host и port, затем разрешить только случай, когда найденная запись имеет тот
же `id`. При конфликте не выполнять SQL UPDATE.

Оставить защиту на уровне API/queries без миграции и без нового UNIQUE-индекса.
Зафиксировать в документации, что уникальность обеспечивается прикладной
проверкой, а индекс `idx_proxies_host_port` остается обычным индексом поиска.

## План реализации

### 1. Нормализация и backend

Проверить callers и изменить минимально необходимые места:

- `src/proxy/index.js` или другой существующий общий модуль:
  - определить переиспользуемую функцию нормализации host;
  - сохранить текущую валидацию формата proxy;
  - не менять типы поддерживаемых прокси и parsing-форматы.
- `src/api/proxies.js`:
  - нормализовать host одиночного создания до `findByHostPort` и `create`;
  - нормализовать host каждого объекта bulk-импорта до проверки и создания;
  - в `PUT /:id` нормализовать входной host, проверить конфликт с другой
    записью и выбросить существующий `conflict(...)` при совпадении;
  - не допустить изменения записи при конфликте.
- `src/db/queries.js`:
  - изменить существующий `findByHostPort`, чтобы SQL использовал
    `LOWER(TRIM(host)) = ? AND port = ?`;
  - принимать нормализованный host как параметр поиска;
  - не вводить новый слой или отдельную сущность;
  - сохранить текущие контракты `create`, `update` и `findByHostPort`, если
    задача решается на уровне API.
- `src/db/schema.js` не изменять.

Нужно отдельно учесть, что старые записи в БД могут содержать host в старом
регистре или с пробелами. Новая проверка должна находить такие записи через
нормализованный поиск, но автоматическую миграцию существующих данных не
выполнять.

### 3. Тесты

Использовать существующий стиль Vitest и тестовые слои проекта. Добавить или
расширить тесты рядом с текущими API/БД тестами, не изменяя существующие
не связанные проверки.

Проверить минимум:

- одиночное создание сохраняет `host.trim().toLowerCase()`;
- одиночное создание отклоняет host с отличающимся регистром как дубль;
- одиночное создание корректно обрабатывает пробелы вокруг host;
- bulk-импорт сохраняет нормализованные host;
- bulk-импорт отбрасывает дубликаты существующих записей;
- bulk-импорт отбрасывает повторяющиеся строки в одном входном списке за счет
  существующей последовательной проверки после каждой вставки; отдельный
  локальный `Set` не добавлять;
- `PUT` отклоняет host/port, занятые другой записью, с HTTP `409` и текущим
  сообщением;
- при конфликтном `PUT` исходная запись остается неизменной;
- `PUT` разрешает сохранение той же записи без ложного конфликта;
- обновление на host с другим регистром приводит к нормализованному значению;
- обычный не конфликтующий `PUT` продолжает работать.

При наличии подходящих интеграционных API-тестов выполнить также их команду

Проверить поиском по репозиторию, что документация больше не утверждает, будто
индекс `idx_proxies_host_port` сам обеспечивает уникальность, и что описание
`POST`/`PUT` согласовано во всех языковых версиях.

## Риски и ограничения

- Без изменения схемы БД остается race condition между предварительным поиском
  и вставкой при конкурентных запросах. Это принятое ограничение требования
  «без изменения схемы».
- Существующие дубли или ненормализованные строки не удаляются и не
  переписываются автоматически. Они будут учитываться при новых проверках по
  нормализованному ключу.
- Смена регистра host в сохраненных данных может повлиять на точные UI/API
  сравнения, поэтому необходимо проверить все callers поля `host`.
