# TASK — Отображение имени профиля в Window Preview и Detected Windows

## Цель

В разделе синхронизации (`Window Preview` и `Detected Windows`) показывать
имя профиля из MultiManager, а не системный заголовок окна Chromium вроде
`Untitled - Chromium`.

Системный заголовок окна сохранить в отдельном поле как диагностический
fallback, но не использовать его как основное отображаемое имя, если профиль
сопоставлен.

## Согласованное решение

1. Использовать существующее сопоставление окон с запущенными профилями по
   PID на backend-уровне.
2. При чтении запущенных профилей построить lookup `PID -> name` из текущего
   результата БД (`profiles.name`, с fallback на `profiles.id` при пустом имени).
3. Для Windows при формировании результата `getRunningWindows()` сопоставить
   PID найденного окна с lookup и вернуть только два имени:

   - `windowTitle` — исходный заголовок окна Windows;
   - `name` — имя профиля из lookup, а при отсутствии сопоставления
     `windowTitle`.

   Дополнительные поля `pid`, `profileId` и `profileName` в ответ endpoint не
   добавлять: существующий UI их не использует, а `profileName` дублировал бы
   вычисленное значение `name`.

4. `WindowArranger.vue` не менять, если проверка подтверждает, что обе зоны уже
   отображают `win.name`. Менять Vue-файл только при обнаружении фактической
   необходимости для использования существующего поля `name`.
5. Не менять логику фильтрации окон, позиционирования, фокусировки,
   синхронизации профилей, БД или запуска Chromium.

## Поведение и границы

- Для каждого окна, относящегося к PID запущенного профиля, отображается имя
  этого профиля.
- Если у одного профиля обнаружено несколько подходящих окон, каждое окно
  получает одно и то же имя профиля.
- Если PID не найден среди запущенных профилей, окно не удаляется: показывается
  его системный заголовок.
- Основной сценарий продакшена — Windows, где сейчас выполняется PID-only
  поиск через Win32 `GetWindowThreadProcessId`.
- Для Linux/macOS не вводить новый механизм определения PID без необходимости;
  сохранить существующее поведение и fallback системного имени.
- Не выводить в UI PID, если это не требуется текущей разметкой; `profileId` и
  `windowTitle` нужны только как данные ответа и для диагностики/будущего
  использования.

## Затрагиваемые файлы

### Backend

- `src/api/window-arranger.js` — создать lookup запущенных профилей по PID;
  передать PID из результата Win32-скрипта в объект окна; добавить
  `windowTitle` и вычислить отображаемое `name`.

### Frontend

- `gui/src/renderer/views/WindowArranger.vue` — только проверить, что preview и
  таблица уже используют `win.name`; ожидается, что файл изменять не потребуется.

### Тесты

- `tests/unit/window-arranger.test.js` — добавить проверки доступного тестового
  шва и source-code инвариантов:
  - endpoint `/windows` по-прежнему возвращает массив окон;
  - Win32-скрипт получает PID через `GetWindowThreadProcessId`;
  - результат PowerShell сохраняет HWND как `id`, координаты и размеры без
    изменения их назначения;
  - backend строит lookup только по запущенным профилям и получает имя из
    `profiles.name` с fallback на `profiles.id`;
  - `windowTitle` равен исходному Win32 title;
  - `name` выбирает имя профиля при совпадении PID и `windowTitle` при
    отсутствии совпадения;
  - ответ не добавляет `pid`, `profileId` или `profileName`;
  - `Focus`, `Grid` и `Cascade` продолжают использовать HWND из `id`;
  - существующие фильтры crash/restore и минимального размера сохраняются.
- При необходимости добавить небольшой unit-тест для преобразования результата
  окон, но не создавать новый production-модуль только ради этого теста.

Не изменять `package.json`, lock-файлы, схему БД, API авторизации и версию
проекта.

Ответ `/api/window-arranger/windows` изменяется добавлением `windowTitle` и
изменением смысла существующего `name`, поэтому обновить референс endpoint во
всех языковых версиях документации:

- `docs/API.md`;
- `docs/API.en.md`;
- `docs/API.zh.md`.

Устаревшее описание `/windows/grouped` в этих документах не исправлять в рамках
данной задачи.

## Проверка результата

1. Запустить целевой unit-тест:

   ```bash
   npm test -- --run tests/unit/window-arranger.test.js
   ```

2. Запустить полный набор unit-тестов:

   ```bash
   npm test
   ```

3. Выполнить ручную проверку на Windows:

   - запустить минимум два профиля с различимыми именами;
   - открыть вкладку синхронизации и нажать `Refresh`;
   - убедиться, что в `Window Preview` отображаются имена профилей;
   - убедиться, что в `Detected Windows` отображаются те же имена;
   - проверить, что имена не заменяются на `Untitled - Chromium`;
   - проверить `Grid`, `Cascade` и `Focus`, чтобы изменение данных имени не
     повлияло на `id` окна и операции управления.

4. Проверить fallback: если окно не сопоставлено с running-профилем, оно
   должно остаться в списке и показывать системный title.

## Риски и ограничения

- PID может быть устаревшим или профиль может завершиться между запросом БД и
  перечислением окон. В этом случае нужен безопасный fallback на системный
  title, без ошибки всего endpoint.
- Одно окно Chromium может иметь дочерние/дополнительные top-level окна с тем же
  PID; каждое подходящее окно будет подписано именем профиля.
- Системный title может содержать разделитель `|`, поэтому существующий формат
  строкового вывода PowerShell нельзя расширять через новый неэкранированный
  title без учёта разбора. Для сопоставления использовать уже выделенный PID
  до формирования ответа; не ломать текущий формат приоритетных полей.
- Имя профиля является пользовательскими данными, но оно уже разрешённо
  отображается в GUI и не попадает в чувствительное логирование. Не добавлять
  его в дополнительные backend-логи.
- Не менять `id` окна: он должен оставаться HWND, иначе `Focus`, `Grid` и
  `Cascade` перестанут работать.

## Критерии приёмки

- В `Window Preview` у обнаруженного окна отображается имя соответствующего
  профиля из БД.
- В `Detected Windows` отображается то же имя профиля.
- `Untitled - Chromium` и другие системные title не используются при наличии
  корректного PID-сопоставления.
- Несопоставленное окно отображается с исходным системным title.
- Ответ содержит только добавленное поле `windowTitle` и существующее поле
  `name` с новым приоритетом профильного имени; поля `pid`, `profileId` и
  `profileName` отсутствуют.
- Операции `Focus`, `Grid`, `Cascade` работают без изменений.
- `docs/API.md`, `docs/API.en.md` и `docs/API.zh.md` описывают обновлённую форму
  ответа endpoint.
- Существующие API, схема БД, security-модель, запуск браузера и версия проекта
  не изменены.
- Целевой и полный unit-тесты проходят.
