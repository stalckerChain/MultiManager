# TASK — Автологин кошелька при ручном запуске профиля

## Цель

При запуске профиля с главной страницы приложения автоматически выполнять
автологин в кошелёк, если у профиля сохранены EVM-адрес и пароль кошелька.
Перед автологином и после него браузер должен быть приведён к состоянию с одной
чистой вкладкой `about:blank`.

## Согласованные требования

- Ручной запуск профиля с главной страницы — вызов
  `POST /api/browser/:id/start` без `run_id`.
- Для разрешения автологина должны одновременно присутствовать непустые
  `wallet_evm_address` и `wallet_password`.
- Если хотя бы одно из двух полей отсутствует или пустое, автологин не
  выполняется; все page-вкладки закрываются, создаётся одна вкладка
  `about:blank`.
- Если оба поля присутствуют, выполняется существующий Zerion-автологин.
- После успешного автологина все page-вкладки закрываются и остаётся одна
  вкладка `about:blank`.
- При ошибке автологина браузер не останавливается: все page-вкладки должны
  быть закрыты, остаётся одна вкладка `about:blank`, ошибка записывается в
  существующий профильный лог.
- Запуск автоматических скриптов через `RunExecutor` и Python-процесс не
  должен получить второй автологин. Для automation-запуска, содержащего
  `run_id`, новое ручное поведение пропускается.
- Пароль, EVM-адрес и полные URL не должны попадать в логи.
- Схему БД, формат хранения данных и API-контракт существующего
  `zerion-login` менять не нужно.
- Чистой вкладкой считать URL `about:blank`.

## Архитектурное решение

Использовать существующий lifecycle запуска в `src/api/browser.js`: после
запуска браузера и загрузки доступных расширений определить ручной запуск по
отсутствию `run_id`, затем выполнить preflight по wallet-полям и автологин.
Не вызывать новый HTTP-запрос из GUI, чтобы последовательность запуска,
автологина и очистки вкладок оставалась атомарной на backend-уровне.

Операцию нормализации вкладок реализовать в существующем
`src/cdp/profile-tabs.js`, не создавая новый сервис или менеджер. Вся операция
`resetToSingleBlankTab(profileId)` — получение списка targets, создание
`about:blank` и закрытие остальных вкладок — должна выполняться внутри одного
вызова `withProfileSession`, чтобы не открывать несколько CDP WebSocket-сессий:

- открыть новую страницу `about:blank`;
- получить page-targets через существующий CDP-клиент;
- закрыть все старые page-targets;
- не закрывать `devtools://` targets;
- гарантировать закрытие WebSocket-сессии в `finally`;
- не логировать URL.

Нормализацию выполнять также в ветке ошибки автологина через `try/finally`,
чтобы ошибка не оставляла вкладку расширения или другие рабочие вкладки.
Ошибка автологина не должна приводить к остановке уже запущенного браузера.

## План реализации

### 1. Backend и CDP

- `src/cdp/profile-tabs.js`:
  - добавить минимальную операцию `resetToSingleBlankTab(profileId)` на базе
    существующих `withProfileSession`, `listPageTargets`, `createTarget` и
    `closeTarget`;
  - сначала создать/сохранить новую `about:blank` вкладку, затем закрыть
    остальные page-targets;
  - обеспечить корректное поведение при отсутствии старых вкладок и при
    частичной ошибке закрытия;
  - экспортировать операцию для backend-кода.

- `src/api/browser.js`:
  - после запуска браузера и загрузки расширений определить `run_id` из body
    или query;
  - для ручного запуска проверить `profile.wallet_evm_address` и
    `profile.wallet_password` без логирования их значений;
  - при отсутствии одного из полей вызвать нормализацию вкладок и завершить
    preflight без вызова `zerionLogin`;
- при наличии обоих полей вызвать существующую логику Zerion-логина;
- перед вызовом существующей логики Zerion-логина вызвать
  `resetToSingleBlankTab`, чтобы убрать стартовые и служебные вкладки;
- после попытки логина всегда вызвать нормализацию вкладок в `finally`;
  - при ошибке логина записать существующую ошибку в профильный лог, сохранить
    запущенный браузер и вернуть согласованное успешное состояние запуска либо
    другой уже принятый контракт без остановки процесса;
  - не запускать новую ручную последовательность для automation-запросов с
    `run_id`;
  - учесть, что операция выполняется после фактической загрузки расширения и
    определения CDP-порта.

- `gui/src/renderer/views/Profiles.vue` и GUI-store не менять, если backend
  полностью покрывает ручной запуск через существующий endpoint.

### 2. Тесты

Добавить или расширить unit/integration-тесты в существующем стиле Vitest:

- ручной запуск с обоими wallet-полями вызывает автологин;
- ручной запуск без EVM-адреса не вызывает автологин и очищает вкладки;
- ручной запуск без пароля не вызывает автологин и очищает вкладки;
- automation-запуск с `run_id` не вызывает новый ручной автологин;
- после успешного логина остаётся ровно одна `about:blank` вкладка;
- после ошибки логина браузер остаётся запущенным и также остаётся ровно одна
  `about:blank` вкладка;
- операция очистки не закрывает `devtools://` targets;
- пароль, EVM-адрес и URL не появляются в логах;
- CDP WebSocket закрывается при успехе и при ошибке.

Использовать существующие тестовые точки для `src/api/browser.js`,
`src/cdp/profile-tabs.js` и интеграционного запуска профиля. Не добавлять
новый тестовый фреймворк или новую зависимость.

### 3. Проверка результата

Выполнить:

```text
npm test
```

При наличии подходящих интеграционных тестов проверить запуск профиля с
реальным/тестовым CDP-контуром и убедиться, что после каждой ручной попытки
количество обычных вкладок равно одной, а её URL равен `about:blank`.

Проверить поиском по репозиторию, что automation-flow не вызывает новый
ручной автологин повторно и что секреты не передаются в новые сообщения логов.

## Риски и ограничения

- Автологин использует существующее plaintext-хранение `wallet_password`; это
  security-sensitive поведение, но модель хранения и API не изменяются.
- Между созданием новой вкладки и закрытием старых возможны внешние изменения
  вкладок; операция должна сохранять новую `about:blank` вкладку как
  единственную целевую.
- Если расширение Zerion отсутствует или runtime ID не определяется, это
  считается ошибкой автологина: браузер остаётся запущенным, вкладки
  нормализуются, ошибка логируется без секретов.
- Существующий automation-flow может иметь собственную логику автологина;
  проверка `run_id` обязательна для предотвращения двойного входа.
